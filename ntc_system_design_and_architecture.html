NTC 2.4.7 · System Design · Architecture

One binary.
Layered by design.

NTC is a shell-first workspace: a Rust binary and library that combine navigation, aliases, pipelines, editing, reporting, networking, databases and a package manager behind one command surface. This page maps the system behind that surface — its layers, runtime path, ownership rules, trust boundaries and extension seams.

02 · Startup path

From process start to prompt.

Startup is intentionally sequential. Configuration, navigation and the shell are ready before the interactive loop begins; the watcher and update check are optional and fail soft.

Step 01 · preparationsynchronous

Process bootstrap

main first ensures the default themes exist, then touches Config::global(). That lazy singleton loads TOML, detects terminal capabilities, configures colour/ASCII fallback and loads the language pack before the CLI route is chosen.

Sourcesrc/main.rs:11
StateConfig singleton, theme registry

Why it matters

Every later layer reads configuration through this singleton. If the TOML is invalid, NTC warns and continues with defaults instead of aborting startup.

03 · Command lifecycle

A line, traced end to end.

The shell is the composition point. It expands shortcuts, recognises its own operators, dispatches builtins and hands everything else to the platform shell — then reconciles state before the next prompt.

Read & edit

rustyline renders a plain-text prompt, keeps history and autosuggest in the loop, and routes Tab / Shift-Tab through the custom hinter. The line is trimmed and BOM-cleaned before anything executes.

Mechanism

rl.readline() → history entry → NTC helper hints. Ctrl-C prints ^C and loops; Ctrl-D exits.

Source

src/shell/entry.rssrc/shell/hinter.rs
empty line → continueCtrl-C → new prompt

Operator semantics

src/shell/pipeline.rs
  • 01Pipes capture one stage and feed the next. ANSI escapes are stripped before the bytes cross the stage or reach a file.
  • 02Logical gates use a dedicated failure marker, not only the return value, so a failed system child is visible to && and ||.
  • 03Redirections support file input/output and inline heredocs. Operators must be whitespace-delimited and outside quotes or brackets.

Output contract

what the next layer receives

Builtins return Result<bool>. The boolean is the shell’s “should exit” signal, not the command’s success bit; failure is carried separately by the pipeline marker.

Unknown commands become platform processes. Their working directory is the Navigator’s CWD, inherited environment is preserved, and child status is translated back into the pipeline contract.

05 · State & persistence

Who owns what, and where it lives.

NTC separates process-global runtime state from per-project configuration and durable files. Most state is either a singleton, a Navigator field, or a plain file on disk.

Config

global RwLock

A single typed configuration value shared by all modules. Reads clone fields; writes take the write lock, mutate and save.

Config::read_global() / write_global()

Session

global RwLock

Last directory, nav stack and editor snapshots. Corrupt files load as an empty session instead of breaking startup.

SessionState::global() — max 24 dir buckets

Navigator

owned value

The shell owns the Navigator and passes &mut through dispatch. Its CWD is kept in sync with the process working directory.

Passed to every command; not a global singleton

Watcher

Arc handle

The shell owns an optional watcher handle. The notify callback owns its own thread and writes into shared atomics/mutexes.

Option<Arc<WatcherHandle>>

Pipeline

static side-channel

Failure state, quiet mode and heredoc bodies are process-level statics because pipeline stages call back into the same dispatcher.

mark_failed(), is_quiet(), heredoc supply

Editor

owned state tree

Buffers, cursor, modes, scroll, sidebar, syntax, terminal and run output all live inside the editor instance.

Snapshots are the only state that crosses process lifetime

06 · Runtime model

Concurrency without a central reactor.

The shell and editor are event loops, not async services. Tokio is available for subsystems that need it; the rest of the runtime uses threads, channels, atomics and short-lived locks around explicit shared state.

Shell main loop

main thread
Poll watcher — drain a debounced summary if one is ready.
Build prompt — directory, watcher marker, Git fragment, venv prefix.
Read line — rustyline blocks for input while keeping hints/history.
Expand + execute — same thread runs builtins or waits for a child process.
Reconcile — update watcher path, invalidate Git cache.

No command runs concurrently with another shell command. Background services report through polling or configured triggers.

Watcher callback

notify thread
Receive event from the platform watcher.
Filter ignored directory segments and non-mutating event kinds.
Buffer pending events behind a mutex; stamp the last event time.
Signal an AtomicBool so the shell’s fast path can skip polling work.

The 400 ms debounce is enforced at poll time on the shell thread. The callback never renders or runs aliases.

Update checker

background thread
Gates — environment flag, config setting, 24-hour throttle.
Fetch — check the latest release over the network.
Report — print a notice only when a newer version exists.
Fail silently — no internet or request failure never blocks startup.

This is intentionally best-effort. Network availability is not part of shell correctness.

Editor + PTY

main + reader threads
Event poll — crossterm keys, mouse and resize at the configured rate.
PTY spawn — portable-pty creates the child and a reader thread forwards bytes.
Parse output — vte builds the terminal grid and alternate-screen state.
Auto-save — snapshot the editor state on the configured interval.

The embedded shell receives NTC_IN_EDITOR=1, so it keeps the PTY’s CWD and never overwrites the outer session directory.

Serve accept loop

main + connection threads
Bind listener — port and bind address come from config defaults.
Accept — non-blocking loop checks a shutdown flag every 200 ms.
Spawn — each connection runs on its own thread with cloned DB/auth handles.
Share state — SQLite access is serialized behind a Mutex<Connection>.

File and HTTP services use the same thread-per-connection shape. Chess service routes have their own connection workers.

Ctrl-C handler

signal callback
Read child PID from a process-wide atomic.
Terminate tree — taskkill /F /T on Windows, kill -TERM elsewhere.
Set shutdown flags registered by long-running services.
Return control to the shell or stop the serve loop.

Installed once through an atomic guard. Flags are registered and unregistered around long-running commands.

Shared-state contract

Cross-thread coordination is deliberately small and explicit. Most domain modules never see these primitives directly.

Config: std::sync::RwLock Session: std::sync::RwLock Watcher: Arc + AtomicBool + Mutex Serve DB: Arc<Mutex<Connection>> Child PID: AtomicU32 Shutdown: Mutex<Vec<Arc<AtomicBool>>> Pipeline: process statics
07 · Trust boundaries

Powerful by default, not sandboxed.

NTC is a local developer tool. It assumes the operator trusts the code they run and the projects they open. The architecture reduces accidental failure, but it does not claim OS-level isolation between commands, scripts, plugins or served content.

Execution authority

Everything runs as your user

no sandboxsame environmentchild tree kill

Builtins, aliases, .ntc scripts and NTCRANFILE targets execute in-process or through the platform shell with the user’s filesystem rights and environment.

Controls: explicit fallback path, failure side-channel, and an active-child PID used by Ctrl-C. Residual: a malicious command or script has the same authority as NTC itself.

Filesystem policy

Ignore rules are guidance, not access control

advisory rulesOS permissions

ntconfig.toml controls what search, tree, scan and report surfaces should skip or care about. Those rules shape tooling; they do not prevent a direct path from being read or written.

Actual enforcement is whatever the operating system grants the current account. Treat a project you open as input you trust.

Credentials

Secrets are local files and process memory

plaintext TOMLrestricted profilesno vault

API keys and user settings can live in the global TOML config. SSH profiles use a dedicated store with restrictive permissions on Unix, but there is no OS keychain or encrypted vault abstraction.

Serve Basic credentials are held in memory for the process lifetime; they are not hashed at rest because they are supplied per invocation.

Network exposure

Serve is a LAN-facing surface

0.0.0.0 defaultAPI-only authno native TLS

File/HTTP services bind all interfaces by default. When --auth is set, every /api/* route requires HTTP Basic, while static assets stay public so the UI can load. Downloads may use a short-lived token.

There is no built-in TLS or rate limiter. Prefer loopback, a trusted LAN, a VPN or a TLS-terminating reverse proxy. --share only advertises an address; it does not change routing or add authentication. The chess service deliberately has no --auth.

Supply chain

Runtime packages are vendor artifacts

remote archivesoptional digestsper-version dirs

ntpkg downloads vendor releases and installers, extracts archives, and may launch OS installers. A SHA-256 verification helper exists, but not every source definition supplies a usable digest.

Installing a runtime is therefore an act of trust in the upstream project and transport. Versioned directories make rollback practical; they do not make the downloaded executable safe.

Parsed content

Project files are untrusted input

parsersno browser runtimegenerated HTML

Reports, sheets, images, Markdown, XML and language-server messages are parsed by third-party crates and external tools. Parser bugs are part of the trust surface even when NTC does not execute the file.

Generated HTML or served files may contain active content. NTC itself does not run a browser, but a browser that opens a served report does.

Operational rule of thumb

Run NTC as a normal user, not an administrator. Keep the config directory private, bind serve to loopback unless you intend LAN exposure, put TLS and access control in front of any public deployment, and review .ntc, NTCRANFILE.toml and installers before running them. Upload limits (10 GB per upload, 100 MB chunks) and idle timeouts reduce accidental resource use; they are availability controls, not authorization.

08 · Failure & recovery

Fail locally, keep the prompt.

Recovery is mostly defensive defaults and scoped cleanup rather than a transaction system. The design goal is that a bad file, failed child or interrupted service does not leave the terminal or the next prompt unusable.

09 · Build & platform matrix

One binary, conditional edges.

The build is a conventional Cargo binary plus library. Portability comes from bundled native dependencies, cfg-gated surfaces and runtime discovery of optional external tools rather than a separate implementation per operating system.

Default feature set

image2doc enables the optional image crate. ocr enables the OCR module, but OCR is still compiled only outside Android and requires a tesseract executable at runtime.

default = image2doc, ocrfeature-gated imageexternal tesseract

Native dependencies

SQLite is vendored through rusqlite’s bundled feature. PTY, clipboard, audio and report writers compile per target; Windows console access uses windows-sys, while Linux clipboard support uses x11rb.

rusqlite bundledportable-ptyrodio

Embedded frontends

rust-embed packages the file-service and chess web assets into the binary. There is no separate Node runtime at execution time, but the dist folders must exist when the Rust project is compiled.

build-time assetsno runtime serversingle deployable

Android / Termux

Native clipboard, PDF, DOCX and XLSX writers are excluded. Terminal clipboard uses termux-clipboard-set when available. OCR is disabled by cfg even though the feature is default.

cfg exclusionsTermux APItext formats remain

Optional runtime tools

Git, language servers, Tesseract, cloudflared and package-managed runtimes are discovered at runtime. Missing tools degrade a feature; they are not linked into the core binary.

which::whichPATH injectionbest-effort

Release verification

A meaningful check covers library tests, the binary build and a manual TUI pass. Terminal behaviour and platform-specific PTY/clipboard paths cannot be fully validated by unit tests alone.

10 · Extension guide

Where a new capability belongs.

NTC grows by adding domain modules and wiring them into the shell, not by centralising every feature in one dispatcher. These recipes follow the seams already present in the codebase.

Add a builtin command

Keep the handler in a focused command module and make dispatch the only central edit.

  1. Implement cmd_* returning Result<bool>.
  2. Add the name/alias arm in execute_single_command.
  3. Add help, hints/completion and at least a parser test.
src/shell/commands/<feature>.rs → src/shell/commands/mod.rs

Add a domain module

Use a module when the feature owns state, parsers or a long-lived service.

  1. Create src/<name>/mod.rs with a narrow public surface.
  2. Declare it in lib.rs; re-export only what other modules need.
  3. Wire commands through shell and gate platform deps in Cargo.toml.
src/lib.rs → pub mod <name>;

Add configuration

Prefer an existing config struct over a new global singleton.

  1. Add a serde-defaulted field to the global or editor config.
  2. Update the default constructor and any migration/merge logic.
  3. Keep project-only values in ntconfig.toml, not the global struct.
src/utils/config/mod.rs → Config / EditorConfig

Add a managed runtime

Package support is data plus an installer, not a new branch in the shell.

  1. Add a source definition with per-platform URL/archive metadata.
  2. Implement or reuse an installer that places binaries under the version dir.
  3. Register the installer and verify PATH injection picks it up.
src/ntpkg/sources.rs → src/ntpkg/installers/

Add a report format

Extend the format enum and generator while keeping collection shared.

  1. Add the variant, extension and binary classification.
  2. Reuse collect_report_files; implement a generator.
  3. Add cfg gates if the writer is unavailable on Android.
src/report/mod.rs → ReportFormat + generator

Add a serve route

Routes live behind one auth gate and one method/body contract.

  1. Add a method/path arm in handle_api.
  2. Reuse ApiResponse, JSON helpers and the DB handle.
  3. Test both locked and unlocked router paths; enforce body limits.
src/shell/commands/serve.rs → handle_api
11 · Architecture observations

What the design optimises for.

Read as an architecture review: the strengths are explicit state and domain ownership; the costs are global seams, platform conditionals and security surfaces that assume a trusted operator.

Strengths

  • +Explicit composition. The shell is a visible dispatch point; domain modules do not need a framework or service registry to participate.
  • +State is named. Config, session, Navigator and watcher ownership are easy to trace and reason about.
  • +Portable core. Bundled SQLite, native PTY and cfg-gated optional surfaces keep one codebase across desktop and Termux.
  • +Degradation is normal. Optional external tools and network checks fail into reduced functionality rather than startup failure.

Tensions

  • !Global seams. Process-level pipeline flags and singleton config are pragmatic but make parallel execution and isolated testing harder.
  • !Dispatch remains central. The command match is the price of a simple shell; a registry would reduce merge pressure but add indirection.
  • !Platform cfgs multiply. Android exclusions and per-OS installers are necessary, but every new dependency must be audited across four target families.
  • !Security is deployment-sensitive. The serve defaults are convenient on a laptop and dangerous on an untrusted network; documentation and safer defaults matter more than clever code.

Good extension points

  • →New domain behaviour belongs in a module with a small public API, reached through a shell command.
  • →New persistent preference belongs in typed config, not an ad-hoc file or static.
  • →New platform capability belongs behind an adapter with a non-Android fallback, not scattered cfg! branches.
  • →New served capability belongs behind the existing auth gate, body limits and response helpers.

Questions worth asking

  • ?Should serve default to loopback, with explicit opt-in for LAN binding?
  • ?Should pipeline failure and quiet mode become per-execution context instead of process statics?
  • ?Should package sources require a digest rather than treating it as optional metadata?
  • ?Should command dispatch become data-driven to make help, hints and completions derive from one definition?
